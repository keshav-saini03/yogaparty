<objective>
Ship the single server action that turns FormData into a `signups` row and redirects to the room. This is the only writer in Phase 2.

Purpose: Plans 03 (landing) and 04 (signup form) both depend on this action existing. Isolating the write into one tiny file keeps Phase 4 (RLS + abuse hardening) and Phase 5 (live counter) easy to reason about.

The action MUST NOT accept, read, or fall back to any `city` value from `formData`. The form has no city input and no city edit UI; the city is informational only on the form.

`signups` table (Phase 1 migration `supabase/migrations/0001_init.sql`):
```sql
CREATE TABLE signups (
  id UUID DEFAULT gen_random_uuid() PRIMARY KEY,
  name TEXT NOT NULL,
  phone TEXT UNIQUE NOT NULL,
  country_code TEXT NOT NULL DEFAULT '+91',
  city TEXT,                                   -- nullable
  referrer_id UUID REFERENCES signups(id),     -- nullable, FK to signups.id
  created_at TIMESTAMPTZ DEFAULT now()
);
```

Important: `referrer_id` has a FK constraint. An invalid (well-formed UUID but absent) value would raise PostgREST error code `23503`. We avoid pre-validating against the DB by regex-checking UUID shape only; if it doesn't match shape, we set `null`. If a well-formed UUID doesn't exist in the table, the insert would 23503 — RESEARCH Topic 3 accepts this risk for hackathon scope but we mitigate by catching `error.code === '23503'` and retrying with `referrer_id = null` once.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Browser → Server action | `FormData` from the form; all fields untrusted strings. Validate before insert. |
| Browser → Server action (referrer) | `referrer_id` originates from `?ref=` URL param via localStorage; arbitrary attacker-controlled UUID. |
| Server action → Postgres | Anon-key insert; relies on schema `UNIQUE(phone)` + `FK referrer_id → signups.id` for integrity. |
| Edge middleware → Server action (city) | `x-geo-city` header is server-authoritative; the action reads it via `getDetectedCity()` only. Client cannot influence the stored `city` value because no `city` field is read from `formData`. |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-02-03 | Tampering | `phone` field accepting non-digit strings (e.g., SQL fragments) | mitigate | Regex `/^\d{6,15}$/` rejects anything not 6-15 ASCII digits before `.insert(...)`. Supabase parameterizes the insert so injection is impossible regardless, but the regex is a cheap defense-in-depth. |
| T-02-04 | Tampering | `referrer_id` field with malicious UUID pointing to attacker's own signup (self-promotion) | accept | Self-referral check requires knowing the not-yet-created signup ID — impossible at write time. Phase 5 leaderboard will be the first place self-referral could be detected; out of scope for Phase 2 per CONTEXT. |
| T-02-05 | Tampering | `referrer_id` non-UUID string crashes the insert | mitigate | UUID regex check; non-matching values become `null` before insert. |
| T-02-06 | Denial of Service | Bot floods `createSignup` with unique phone numbers, fills DB | accept | CONTEXT explicitly defers rate limiting / captcha to Phase 4 or later. Supabase free tier (500MB) absorbs reasonable abuse for a 48h hackathon. |
| T-02-07 | Information Disclosure | `console.error(error)` leaks PII or DB schema in logs | mitigate | Log only the error object, not the form data. Server console only — never returned to client. Generic `'Something went wrong'` returned to user. |
| T-02-08 | Repudiation | No audit trail of who submitted what | accept | `signups.created_at` + `signups.id` is sufficient identity for hackathon scope. Vercel/Supabase logs cover the rest. |
| T-02-08b | Tampering | Client supplies `city` in `formData` to spoof location and game leaderboard | mitigate | Action does not read `city` from `formData`. Sole source is `getDetectedCity()` (Vercel Edge `x-geo-city` header). Client-supplied city values are silently ignored — no field name in the action references them. Grep gate in the verify step enforces this. |
</threat_model>
